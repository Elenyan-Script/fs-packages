# @script-development/fs-router

## 0.3.0 — 2026-08-29

### Minor Changes

- **`RouterView` no longer paints a false `404` before the first navigation resolves.** vue-router seeds `router.currentRoute` with its exported `START_LOCATION` sentinel and replaces it only when a navigation _finalizes_. `START_LOCATION.matched` is empty, so `RouterView` took the unmatched branch and rendered the not-found fallback — the bare `404`, or a consumer's `notFoundComponent` — for the whole window between `mount()` and that resolution. With a lazily-imported page component or an awaiting `beforeEach` middleware, that window spans at least one painted frame on every cold load. `RouterView` now renders nothing (a comment node) while a navigation is **in flight** and the route is still the sentinel. Both halves are load-bearing: the sentinel check is an **identity** comparison against vue-router's exported value, never a `matched.length === 0` shape heuristic (an empty `matched` also describes a genuine miss, which keeps its existing behaviour — see the terminal-path entry below for what it took to make that true on the real navigation path); and the in-flight half is what tells the pre-navigation window apart from a route that is pinned to the sentinel because nothing is coming. A middleware that cancels the first navigation without redirecting pins it forever, and a service nobody navigates never leaves it — both render the ordinary fallback, exactly as before `0.3.0`.
- **Readiness is a fact the service owns, and it is redirect-aware.** fs-router dispatches a middleware redirect by **aborting** the pending hop and pushing the target itself, which vue-router records as a failure — so `router.isReady()` cannot be used to answer "did the app get off the ground?": it mislabels every redirecting first navigation as a failed one, and `markAsReady(error)` then leaves its own `ready` flag false with an emptied handler list, so a later call never settles. The service therefore tracks the in-flight window itself, and a hop whose **successor is already in flight** ends nothing — that covers both a redirect this wrapper dispatched and a hop a later navigation overtook (vue-router's `cancelled` failure). The consequences: an app whose initial-route guard redirects (the ordinary auth-guard shape) paints no not-found frame mid-chain and logs nothing; a navigation that overtakes the first is ordinary routing, not a failed cold start; and a **genuine** first-navigation failure falls through to the fallback with exactly one fs-router console line — a path that previously had no fs-router signal at all.
- **New method: `isReady()`.** `() => Promise<void>`, resolving once the first navigation has settled. It does **not** delegate to `router.isReady()`, for the reason above: it is a service-owned promise, created at construction and **resolved — never rejected —** on both success and genuine failure. It stays pending while nothing has been dispatched.
- **The in-flight window ends on every terminal path, not just `afterEach`.** vue-router has three ways a navigation can end and `afterEach` is only one of them: a guard that **throws** is routed through `triggerError`, which skips `afterEach` entirely, and `router.push({name})` throws **synchronously** for an unknown route name. Closing the window from `afterEach` alone therefore left a thrown guard with the window open forever — a **permanently blank page** and an `isReady()` that never settled. This matters far beyond consumer middleware: fs-router's own `normalizedRouteToSpecificRoute` throws for any unmatched path and is called from its `beforeEach`, so **every cold load of an unknown URL** took that path. The window is now ended by a single idempotent closer reached from all three: `afterEach` (with both supersession clauses unchanged), `router.onError`, and a `try`/`catch` around the push inside `goToRoute`/`replaceRoute`. A thrown guard is treated as a genuine failure — the not-found fallback paints, one fs-router console line is emitted, and `isReady()` settles. Registering an `onError` handler also retires vue-router's own `[VUE_ROUTER_R0010]` warning — and, as the entry below records, rather more than that. **Correction to this release's first entry as originally written:** genuine misses did _not_ keep their prior behaviour on the real navigation path until this change — a cold load on an unknown URL rendered `main`'s visible `404` before `0.3.0`, and blanked in between. The specs that asserted otherwise mounted an un-navigated service, which reaches the fallback through a different branch.
- **Programmatic navigation opens the window too.** `install()` set the in-flight flag synchronously before its push, because guards only run on a later microtask; `goToRoute`/`replaceRoute` did not. A consumer whose _initial_ navigation is programmatic rather than location-driven — a landing bounce, a stored deep link — therefore painted the not-found fallback for a frame. Both now open the window at the top of the call, before the route location is even built. The close is in a `catch`, never a `finally`: the hop fs-router aborts in order to dispatch a middleware redirect resolves while its successor is still running its guards, and closing there would reopen exactly the false-`404` frame this release exists to shut.
- **Reporting a failure survives the settle latch — every navigation, not only the first.** Registering `router.onError` above did more than route a terminal path: `triggerError` emits its own `console.error(error)` **only while no error listener is registered**, so from the moment fs-router registers one it owns the reporting duty for the whole life of the service. Ending the in-flight window is a once-per-service fact and is latched; reporting a failure is not, and putting both behind the same latch meant every genuine failure after the first was **silently dropped**. `goToRoute`/`replaceRoute` callers could still see the rejection on the returned promise, but **history-driven navigation — `goBack()`, browser back/forward, any `popstate` — returns no promise to anyone**, so a middleware that threw there produced no output on any channel. fs-router now emits exactly one `console.error` for every failure that reaches `onError`, first navigation or later. The two channels stay distinct on purpose: a **cancelled** navigation is ordinary guard behaviour and keeps its first-navigation-only `console.warn` (reporting every cancelled hop would turn an auth guard into a console stream), while a **thrown** navigation is an error and is reported as one. This is ADR-0048's shape — _Error Feedback Must Reach the User — the Silent-Failure Contract_. **Correction to the entry above as originally written:** a thrown guard's line is a `console.error`, not the `console.warn` that entry described, and it is emitted on every navigation rather than once.
- **One fs-router console line per genuine failure, redirect chains included.** A middleware redirect is dispatched as its own navigation with a `.catch` attached to it, so a redirect into a target whose guard throws was visible to two reporters at once — `router.onError`, which covers everything vue-router routes through `triggerError`, and that `.catch` — and both fired, describing one failure at two levels of context. The same doubling appeared on a cold load of a redirect to an **unknown route name**, where the first-navigation warn and the redirect reporter each carried it on a different channel. The multiplicity was never a fixed number: **which** reporters are in play depends on the chain's shape, so the rule is positional rather than a count — a reporter records the failure it reports, and the redirect reporter stays silent for a failure someone already reported. Ordering is guaranteed rather than lucky: `triggerError` calls its error handlers synchronously and only then returns a rejected promise, so `onError` has always recorded by the time the `.catch` runs. The redirect reporter is deliberately **not** removed, which is the obvious route to one line and the wrong one — `router.push({name})` throws **synchronously** for an unknown route name, nothing is routed through `triggerError`, and `onError` never sees it, so that reporter is the only one that path has; deleting it would reopen the silent failure the entry above exists to close. One exception, taken knowingly: the ledger of already-reported failures is keyed by object **identity**, so a non-object throw (`throw 'boom'`) cannot be recorded and is reported by every reporter that sees it. The alternative, a value-keyed ledger, would let two navigations that happen to throw the same string suppress each other — a silent drop, which is the worse failure. **Correction to the two entries above as originally written:** "exactly one fs-router console line" was true of every path those entries tested and false of a middleware redirect into a failing target, which emitted two from `0.2.0` onward. It is true as written from this change, with the non-object throw as the single stated exception.
- **`install()` returns the navigation promise.** Its type widens from `() => void` to `() => Promise<NavigationFailure | void | undefined>` — whatever `router.push` returns — so a consumer may `await routerService.install()` before `mount()` and never render the pre-navigation window at all. Widening a return from `void` is assignability-safe, so every existing `routerService.install()` call site keeps compiling and behaving identically.

- **The in-flight window counts concurrent hops, and a failure nothing else reported is reported once.** Two navigations can be outstanding at the same time — a redirect chain always has two, and nothing stops a consumer dispatching two hops in one turn — and the window was a **boolean**, so whichever hop ended first closed it for both. It is now a count, and the two facts that were fused behind one function are separated: **ending a hop** decrements the count and every terminal path does it unconditionally, while **settling readiness** stays a once-per-service latch each terminal path decides separately whether to trip. Three consequences. (1) `router.onError` — the terminal path a thrown guard takes, and the only one `afterEach` never sees — carried none of the supersession checks `afterEach` has: a hop whose guard threw after a successor overtook it settled readiness on the spot, so a consumer awaiting `isReady()` before `mount()` mounted on the sentinel. It now defers while any other hop is still running, which is the only form of that check it can express (it is handed neither a `to` nor a `failure`). (2) A hop a later navigation **overtook** no longer consumes a redirect mark it never placed. vue-router cancels an overtaken hop **before** its guards run, so with two hops dispatched to one redirecting path only the overtaker marks anything — and the cancelled hop's `afterEach`, which fires first and read the mark before its own `failure`, drained it, leaving the hop that placed it to read itself as an ordinary abort and warn that the first navigation had failed. On a navigation that in fact succeeded. The `failure` is now read first, and only a hop that could have placed a mark consumes one. (3) A push to an **unknown route name after startup** reached no reporter at all: it throws synchronously, so nothing is routed through `triggerError` and `onError` never sees it, and the settle latch has already closed. It was visible solely as the caller's rejected promise — which `RouterLink` drops. `goToRoute`/`replaceRoute` now carry a last-resort reporter that defers to whoever recorded first; the redirect dispatch opts out of it, because it has its own reporter that names the redirect. **Correction to the fifth entry above as originally written:** the close is now in a `finally` after all, and the reason that entry gave for refusing one was sound only under the boolean — a successor's dispatch is counted in synchronously before its predecessor can be aborted, so the count never reaches zero across a chain. **Correction to the second and fourth entries as originally written:** "a hop whose successor is already in flight ends nothing" and "both supersession clauses unchanged" described `afterEach` and were asserted of the window as a whole; `onError` implemented neither until this change.

**Consumer note.** All of it is additive; no consumer has to change anything. `await routerService.install()` before `mount()` if you want no first-paint window at all; either way `RouterView` now renders nothing until the first navigation settles, rather than a `404`.

## 0.2.0 — 2026-07-06

### Minor Changes

- **Middleware redirect-return.** A before-route middleware may now return a typed redirect object instead of just a boolean. Returning `{name, id?, query?, parentId?, replace?}` **cancels the pending navigation and navigates to the target in one step** — `goToRoute` (push) by default, or a replace when `replace: true`. A boolean return keeps its exact meaning (truthy cancels, falsy continues), and an object return short-circuits the middleware chain identically to a truthy boolean. This retires the hand-rolled cancel-then-`goToRoute` two-step consumers wrote against `registerBeforeRouteMiddleware`. Additive and backward-compatible: widening the middleware's return union is assignability-safe, so every existing `(to, from) => boolean` middleware still satisfies the type. New exports: `MiddlewareRedirect` and `BeforeRouteMiddlewareResult`.
- **New export: `replaceRoute`.** A replace-semantics sibling of `goToRoute` with the identical signature (`name, id?, query?, parentId?`), delegating to `router.replace` with the same param resolution. Use it for landings that should not pollute the history stack (OAuth callbacks, 404-home bounces, dead-read redirects) — where a push would leave the consumed URL reachable via Back.
- **New option: `notFoundComponent`.** `createRouterService(routes, { notFoundComponent })` lets `RouterView` render a declared component in place of the bare `404` fallback when no route matches at the requested depth. The default (a bare `404`) is unchanged when the option is omitted.
- **`RouterLink` attribute fallthrough.** `RouterLink` now explicitly forwards consumer-set attributes (`class`, `style`, `data-*`, `aria-*`, …) onto the rendered `<a>` via `inheritAttrs: false` plus an explicit attrs merge, keeping the owned `href` and `onClick` authoritative. `class` and `style` already fell through under Vue's automatic single-root attribute inheritance (Vue special-cases and concatenates them); the real defect this closes is that a **consumer-supplied `href` silently overrode the computed navigation `href`** — Vue's automatic merge lets an external non-class/style attribute win, so `<RouterLink :to="…" href="…">` would navigate to the wrong target. Merging fallthrough attrs _before_ the owned props makes the computed `href`/`onClick` win, and non-navigational attrs (`class`, `data-*`, `aria-*`, …) still land on the anchor.
